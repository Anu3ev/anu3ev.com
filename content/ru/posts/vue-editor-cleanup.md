Редактор хорошо проверяет frontend-архитектуру на прочность. Он долго остаётся открытым, создаёт временные controls, меняет документ, запускает асинхронные операции и может закрыться раньше, чем они завершатся.

В работе над редактором изображений сложные ошибки часто находились между этими событиями. При первом открытии canvas выглядел нормально. Проблема появлялась после повторного открытия, отмены crop или завершения старого запроса.

## Начать с владельца

Для каждого ресурса важно знать, кто его создаёт и когда он перестаёт быть нужен этому владельцу. Это не только сам canvas:

- слушатели document и window;
- observers и таймеры;
- object URLs импортированных и экспортированных файлов;
- подписки на события редактора;
- асинхронные операции, которые ещё могут вернуть результат.

Компонент панели инструментов не становится владельцем ядра автоматически. И composable на уровне модуля не должен случайно превращать два экземпляра редактора в одну общую сессию.

## Связать создание и освобождение

Для слушателя, принадлежащего одному mounted-компоненту, Vue даёт понятную границу:

```ts
const viewport = useTemplateRef<HTMLDivElement>('viewport')

/** Измеряет видимый контейнер; у скрытого или размонтированного viewport нет актуального размера. */
function updateViewportSize() {
  const element = viewport.value
  if (!element) return

  editor.resize({ width: element.clientWidth, height: element.clientHeight })
}

onMounted(() => {
  window.addEventListener('resize', updateViewportSize)
})

onBeforeUnmount(() => {
  window.removeEventListener('resize', updateViewportSize)
})
```

Это частичный пример: `editor` — существующий экземпляр, чей resize принимает размер контейнера. Фрагмент показывает владельца слушателя, а не готовую реализацию responsive canvas. Реальному редактору могут понадобиться ResizeObserver и отдельные правила для скрытого контейнера нулевого размера.

## Cleanup не равен отмене запроса

Удаление слушателя не останавливает уже начатый запрос. AI-операция или upload могут закончиться после переключения активного документа.

Перед публикацией результата в состоянии нужно проверить его владельца. В зависимости от операции это abort signal, идентификатор документа или снимок поколения. Важен порядок: дождаться результата, убедиться, что его сессия актуальна, затем применить.

Отмена браузерного запроса также не доказывает, что сервер остановил обработку. Интерфейс должен учитывать эту разницу.

## Проверить второе открытие

Первый рендер — лишь одно состояние системы. Полезно открыть и закрыть редактор дважды, сменить документ во время операции, отменить взаимодействие и восстановить состояние через undo.

Я предпочитаю несколько тестов этих границ множеству проверок вызова собственного helper-а компонента. Ошибка важна потому, что пользователь получает устаревший результат, дублирование команд или ресурс, который никогда не освобождается.
