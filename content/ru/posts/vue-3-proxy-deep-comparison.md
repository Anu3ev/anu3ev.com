В админ-панели inSales владельцы магазинов работают с товарами, заказами, доменами и аналитикой, а магазинов на платформе более 60 000. Летом 2026 года админ-панель переводили с Vue 2 на Vue 3, и после перехода часть интерфейса стала заметно медленнее. Дровер подбора домена, выдвижная панель в разделе «Домены», открывался примерно за 4 секунды, а в продакшене на Vue 2 примерно за 1 секунду.

Переход вела другая команда. С Proxy во Vue 3 я уже сталкивался: когда я переводил на Vue 3 свой редактор инфографики, из-за него сломалась часть интерфейса. Свои задачи я к тому времени закончил, поэтому 7 августа 2026 года предложил команде помощь и взял задачи по странице доменов.

Новой работы Vue 3 в дровер не добавил. Медленный код работал в нём и на Vue 2, а после перехода каждое чтение данных в этом коде стало дороже.

## Задержку создавал общий автокомплит

В дровере есть автокомплит `ui-autocomplete2`, поле с подсказками из UI-кита, библиотеки компонентов интерфейса inSales. На каждом рендере в него передавалось около 700 доменных зон, например .ru или .com. Компонент дважды перебирал их, сравнивал и кешировал.

На Vue 2 этот рендер тоже был медленным и занимал около секунды, поэтому проблема была не так заметна. На Vue 3 те же операции занимали около 4 секунд.

## Vue 3 читает свойства через Proxy

Во Vue 2 реактивность добавлялась прямо в исходный объект: Vue устанавливал на его свойства геттеры и сеттеры. Реактивный объект и исходный были одним и тем же объектом:

```js
const zone = { value: 'ru', text: '.ru' }

Vue.observable(zone) === zone // true
```

Vue 3 исходный объект не меняет, а создаёт для него Proxy, объект-посредник, который перехватывает каждое обращение к свойствам:

```js
import { reactive, toRaw } from 'vue'

const zone = { value: 'ru', text: '.ru' }
const reactiveZone = reactive(zone)

reactiveZone === zone        // false
toRaw(reactiveZone) === zone // true
```

Каждое чтение свойства у Proxy проходит через обработчик Vue. Если чтение происходит во время рендера, Vue ещё и запоминает прочитанное свойство как зависимость компонента. Одно такое чтение почти ничего не стоит. Но код, который дважды перебирает и сравнивает 700 объектов, читает их свойства тысячи раз, и каждое чтение теперь дороже.

## Исправлять нужно было в UI-ките, а не на странице доменов

Медленный код находился внутри `ui-autocomplete2`, поэтому правка на странице доменов ускорила бы один дровер, но не помогла бы остальным автокомплитам. Исправление я внёс в сам компонент, в ветку UI-кита для Vue 3, в тот же день, когда взял задачу.

В дровере подбора домена автокомплит работает в локальном режиме: весь список зон уже передан ему в `items`, и искать на сервере не нужно. Но при инициализации компонент всё равно перекладывал этот список в кеш, а значит, перебирал и сравнивал 700 зон через Proxy. Кеш нужен только для поиска через запросы к серверу, поэтому в локальном режиме я убрал его заполнение:

```js
initCachedItems() {
  // В локальном режиме список уже передан в items, кешировать нечего.
  if (!this.externalSearchEnable) return

  this.setCachedItems(this.getInitialCachedItems())
}
```

Именно эта правка убрала задержку при открытии дровера: операцию, которая не нужна, проще не выполнять, чем ускорять. Быстрее, чем на Vue 2, дровер не стал, но вернул прежнюю скорость.

## Сравнение Proxy с исходным объектом проходит по всем свойствам

Proxy замедлял и кеш автокомплита. В файле `set-cached-items.js` автокомплит кеширует найденные элементы и сравнивает их функцией `isEqual` из Lodash. При этом прокси-объекты сравнивались с исходными объектами.

`isEqual` сначала проверяет, не один ли это объект, и в этом случае сразу возвращает `true`. Proxy и исходный объект для этой проверки разные, поэтому `isEqual` сравнивает их по свойствам. Данные у них одинаковые, так что сравнение не может остановиться на первом различии и проходит все свойства, а каждое чтение у Proxy идёт через обработчик Vue:

```js
import isEqual from 'lodash/isEqual'
import { reactive, toRaw } from 'vue'

const zone = { value: 'ru', text: '.ru' }
const reactiveZone = reactive(zone)

isEqual(reactiveZone, zone)        // true после сравнения всех свойств через Proxy
isEqual(toRaw(reactiveZone), zone) // true сразу: это один и тот же объект
```

Такое сравнение, скорее всего, замедляло все автокомплиты с поиском через запросы к серверу. Поэтому я предложил приводить прокси-объекты к обычным перед сравнением:

```js
import isEqual from 'lodash/isEqual'
import { toRaw } from 'vue'

/** Сравнивает элементы кеша по данным, не читая их свойства через Proxy. */
function isSameItem(first, second) {
  return isEqual(toRaw(first), toRaw(second))
}
```

`toRaw` возвращает исходный объект для Proxy и сам объект для обычного, поэтому отдельная проверка через `isProxy` не нужна. Если оба аргумента ведут к одному исходному объекту, `isEqual` вернёт `true` на первой же проверке.

## Proxy замедлил и чекбоксы в форке Vuetify

Когда я рассказал команде перехода про автокомплит, мне дали ещё одну задачу с похожей проблемой. В аналитике чекбоксы в компоненте `ui-path-list` реагировали на нажатие примерно через 5 секунд. Причину я нашёл в форке Vuetify, собственной копии библиотеки компонентов Vuetify, которую использует inSales: Vue 3 создавал Proxy почти для всего, что компоненты форка хранили в `data`.

Чтобы это исправить, почти всё в `data` нужно было обернуть в `markRaw`. Эта функция помечает объект, и Vue не создаёт для него Proxy. Вотчеры записывали в `data` новые значения, поэтому эти записи нужно было обернуть так же, иначе Vue создал бы Proxy для каждого нового значения. Схематично это выглядит так:

```js
import { markRaw } from 'vue'

export default {
  data() {
    return { nodes: markRaw([]) }
  },
  watch: {
    items(newItems) {
      this.nodes = markRaw(buildNodes(newItems))
    }
  }
}
```

У `markRaw` есть цена: Vue не отслеживает изменения внутри помеченного объекта. Интерфейс обновится, когда свойству `nodes` присвоят новый массив, но не заметит изменения отдельного элемента внутри него. Поэтому `markRaw` подходит для данных, которые заменяются целиком.

Исправление я подробно описал в задаче 10 августа 2026 года, и команда перехода внесла его в форк в тот же вечер.

## Что проверить после перехода на Vue 3

Обе задержки, в 4 и 5 секунд, возникали в общих компонентах, а не на отдельных страницах. Медленный общий компонент замедляет все страницы, где он есть, поэтому и исправлять его нужно в UI-ките или форке, а не на каждой странице по отдельности.

После перехода на Vue 3 стоит проверить места, где:

- код перебирает и сравнивает большие списки реактивных объектов, например через `isEqual`;
- компонент хранит в `data` большие структуры, которые заменяются целиком и не требуют отслеживания по частям;
- в реактивном состоянии хранится инстанс сторонней библиотеки.

Последний случай приводит не к задержкам, а к ошибкам. Так было в моём редакторе инфографики: интерфейс отслеживал свойства инстанса редактора, и во Vue 2 это работало, потому что геттеры и сеттеры устанавливались прямо на инстанс. Во Vue 3 отслеживание через Proxy перестало работать, поэтому я стал хранить инстанс без глубокой реактивности, а изменения для интерфейса теперь приходят через события редактора.

Если после перехода интерфейс стал медленнее, полезно сравнить его скорость с продакшеном на Vue 2. Дровер подбора домена и раньше открывался около секунды. Медленный код был в нём и до перехода, а с Proxy он стал заметен.
