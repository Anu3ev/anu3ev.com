Browser editor performance

Moving a browser editor’s image history from base64 to Blob URLs

Large image strings made undo and redo heavier, slowed interaction, and mixed binary data with the editor’s domain state. The fix changed more than the image loader.

English and Russian · 5 min read

Image history looked straightforward when the editor was small. A canvas object could keep its source as base64, and a history snapshot could serialize the whole object. Restoring a previous state did not need another API request.

That representation became expensive as the editor started handling larger images, templates, copy and paste, AI-assisted image operations, and longer editing sessions. The history model was storing large strings again and again. Work that appeared to be ordinary state management also became image processing on the browser’s main thread.

The problem was inside the state model

The first temptation was to treat slow undo, export, or initial loading as separate performance problems. They had the same source: image bytes had become part of the object model.

That affected several paths at once:

  • history snapshots contained large image strings;
  • restoring an object could repeat conversion and loading work;
  • export competed with editing on the main thread;
  • templates and local browser storage reached practical limits;
  • cleanup was unclear because image data and editor state had the same lifetime.

A loading indicator could hide some waiting. It could not make the representation cheaper.

Moving image data outside serialized history

Blob URLs gave the canvas a browser-readable image source without putting the full encoded image into every serialized object. History could keep the information required to restore the object while the actual image resource lived in a cache with its own lifecycle.

This separation also made ownership clearer. Canvas state described the image object. The resource layer loaded and cached image data. Product integration could still attach its CDN URL and domain data without teaching every history path how to upload or fetch files.

Undo and redo could reuse a cached Blob URL instead of repeating a network or storage request. Initial images were preloaded before they were needed by the editor. The same idea helped template application and state restoration because those paths no longer rebuilt image resources independently.

Heavy work moved away from the visible canvas

Changing the stored source was only part of the fix. Raster conversion and large export operations still had enough work to interrupt interaction.

Web Workers handled suitable background processing. Export used a background canvas clone, so preparing the file did not need to mutate the canvas the user was editing. This mattered for more than responsiveness. Export should not change selection, viewport position, object state, or the next history entry.

Boundary

The confirmed result is qualitative. The changes kept heavy work off the main thread and improved responsiveness, but I do not have a measured percentage that would support a more precise claim.

Object URLs need an explicit lifetime

Blob URLs are not free storage. The browser keeps the underlying resource available until the URL is revoked or the document is unloaded. Revoking too late leaks memory. Revoking too early breaks an object that is still reachable through history, a template, or a pending operation.

The editor therefore needed clear cleanup points. Replaced resources could be released after no live or historical state referenced them. Destroying an editor instance released its managed Object URLs and listeners. Caches also needed to distinguish a reusable resource from stale data left by a closed editor.

This was especially important in an administration product where an editor could open in a modal, close, and open again without a full page reload.

Storage and mobile browsers exposed the same issue

Large custom templates had previously been kept in localStorage. That approach stopped being reliable as template data grew. In another part of the product, repeated IndexedDB and storage calls made mobile Safari initialization extremely slow for AJAX product flows.

Those cases reinforced the same boundary: browser storage is useful, but it should not quietly become the runtime model for every image and every state transition. Batch initialization, preloading, and narrower persisted data reduced repeated work without pretending that storage access was free.

What needed to be tested

The change crossed import, history, restore, export, template, and destruction paths. A successful image import did not prove the full contract.

The relevant tests covered questions such as:

  • Does undo restore the same image without another unnecessary load?
  • Does copying or applying a template preserve domain data and image state?
  • Does export leave the visible editor unchanged?
  • Are cached resources available for the whole history lifetime?
  • Does destroying the editor release resources that are no longer reachable?
  • Do Safari fallbacks preserve the same user-visible result?

Jest covered focused state behaviour, while Playwright exercised the browser interactions and lifecycle paths that depended on real canvas and browser APIs.

The trade-off

Base64 was easy because the data travelled with the object. Blob URLs required a resource registry, caching rules, cleanup, and a clear distinction between persisted data and runtime resources.

That extra structure was justified once images were large enough and history was important enough. The editor stopped treating binary data as ordinary application state, and the responsibilities became easier to reason about across import, restore, export, and destruction.
